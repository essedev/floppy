# Roadmap

The principle is the one in [ARCHITECTURE.md](ARCHITECTURE.md#guiding-principle): build only what the previous step proved necessary. Work already done is in [CYCLES.md](CYCLES.md), the decisions in [DECISIONS.md](DECISIONS.md).

## 1. The system online (next)

The first instance runs on Dokploy (CYCLES 11): the control plane, the admin web and the meta service behind Dokploy's shared Traefik, one certificate per disk name, mail through SMTP, and the team's first disk in manual mode on OVH Milan with bucket versioning (old versions kept 7 days). Simone's Mac mounts it from the `v0.1.1` cask, the spike's measures ran on it (ROADMAP 2), and Dokploy backs up PostgreSQL and the metadata every night, with a restore tried (ARCHITECTURE, Backup and resilience). Left, in order:

1. **The team on it**: invitations from the admin web with access to the disk; each person installs with `brew install --cask essedev/floppy/floppy`, sets the instance's address and signs in.
2. **Small things seen on the way**: a change of access reaches the app at its next heartbeat, up to 60 s later; the Finder's sidebar may keep showing nothing after the share is remounted by name until the Finder is relaunched; a failed mount leaves a Finder dialog that blocks the engine until someone clicks OK; the SMB password between Mac and VM is in `osascript`'s arguments (to the Keychain).

## 2. Data path on OVH

The data-path spike is closed (CYCLES 8, DECISIONS #15): on a simulated 100 Mbps link cold reads over SMB reach 86-93% of the line, a cold seek 0.38 s, the first read after a jump 0.40 s. On the first instance (ARCHITECTURE, Measured performance, 18/10/2026): cold reads at 41 MB/s, a cold seek 0.19 s, 20 s of playback started cold in 0.07 s without stalls, no mtime stall during a copy. Left: cold reads are a quarter of a 1.3 Gbps line (readahead against 20 ms to S3), and small files cost about 200 ms each to write; neither blocks the pilot.

## 3. Build

The team version works end to end on a local stack (CYCLES 10): control plane, meta service, admin web, app and engine, with per-disk access.

- **Design on paper**: [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) is built (migrations 0001-0003), and ARCHITECTURE.md has the control plane, access, storage modes, deploy, team disks and resilience. Left: the rest of the team architecture from [architecture.html](architecture.html) into ARCHITECTURE.md (flows, app states, failure modes, the three ways to run it), and architecture.html itself still draws the key scopes of DECISIONS #22 instead of #24.
- **Fast failure when a file cannot be read**: with the network down, a read of blocks not in cache waits for JuiceFS's retries and for the Mac's SMB timeout, which Floppy raised to 600 s. It should fail at once, the way JuiceMount refuses reads of files not kept offline in 4-67 ms from a local index. It needs to know, per path, what is in the cache; `floppy warmup` loads it but does not record it.
- **Two people on one disk** (measured on the spike, 18/10/2026): an open Finder window never shows a colleague's new file (still missing after 70 s), because Samba notifies only changes made through its own VM, and the VM's replica already has it in 0.1 s; a clip being copied by a colleague is visible from the first second at 0 bytes and grows in 64 MB steps; the Finder deletes at once (no Mac Trash) and JuiceFS's `.trash` is hidden, so a deleted file comes back only through Simone; a save that rewrites a file in place leaves no copy in the trash (a save by rename does). Other people's changes in an open Finder window work in a spike (18/10/2026): the VM's replica emits key events (`notify-keyspace-events`) with the inode of the changed folder (`d<inode>`, the folder's `st_ino`), and a message to Samba's `notifyd` (`MSG_SMB_NOTIFY_TRIGGER`, 0x031B, the same in Samba 4.17, 4.21 and 4.22) made the Finder show a colleague's file at once. It needs `kernel change notify = no`, or `notifyd` drops a trigger sent from its own machine as already covered by inotify, and the option is read only when `smbd` starts. To build: a service per VM that listens to the replica, maps the inodes of the folders the Finder watches (`smbstatus --notify`) and sends added, removed and modified, so a clip being copied also grows in the window. Then the trash with restore and the disk's activity, built on Samba's audit in each VM (DECISIONS #27); restoring one entry is a rename out of `.trash` that refuses a taken name (checked on the spike, 19/10/2026).
- **Keep on this Mac**: only if, in the pilot, a project prepared with "Make available" turns slow again. The cache drops blocks only when it is full or after 30 days (`CACHE_EXPIRE`), and whether a team fills it is not known yet; LucidLink and Dropbox let a folder be kept on the Mac. It needs the same per-path record of the cache as fast failure.
- **The Mac stays awake while data moves**: `caffeinate -i` during a copy, an upload or a warmup, released a couple of minutes after the traffic stops (as JuiceMount does), so sleep does not cut a transfer halfway. No administrator rights needed.
- **Keeping the JuiceFS patches alive**: JuiceFS stays pinned (v1.4.1) and moves only when a release brings something we need (a security or bug fix, performance), not with every Floppy release. The patches (0001 metadata replica, 0002 whole-block reads, 0003 keys from the environment) move from the files in `spike/juicefs-replica/` to a branch of a fork (`essedev/juicefs`), one commit per change, so an update is a rebase. A scheduled GitHub Actions job applies them to each new JuiceFS release and runs the Go tests, so a break shows up before we need the update. An update ships only after the Go tests, JuiceFS's own Redis metadata tests and the acceptance suite pass, and after a run with mixed versions (some Macs on the old JuiceFS, some on the new, one Valkey); if mixed versions do not hold, the control plane enforces a minimum version. Checked on 17/10/2026: no JuiceFS release after v1.4.1 yet; against `main` (212 commits later) 25 of the patch's 27 hunks in `redis.go` apply, and `doCleanStaleSession` and `doRemoveXattr` conflict.
- **Control plane**: phases 1 and 2 and per-disk access are done (`server/`, CYCLES 9 and 10). Left: a nightly `juicefs dump` and `pg_dump` by the control plane for instances outside Dokploy, with the last success in the admin web; before a team keeps its only copy there, the nightly copy of the bucket to a second provider (the first instance's disk is on a bucket with Object Lock, which covers a misused key but not the provider account); the OVH, AWS and MinIO adapters (Garage is built), a shared store for rate limits (with the hosted service), and cleanup of provider keys orphaned by a failed commit.
- **The disk in the web**: browsing a disk, its trash and its activity from the web, for whoever has access to that disk (restoring with write access), so a deletion can be fixed away from the Mac. Listing folders, the trash and restores touch only the metadata, which the meta service already holds; the activity reaches the control plane anyway (DECISIONS #27). Previews and downloads cost more: JuiceFS keeps files as blocks, so a file must be put back together on the server (a JuiceFS mount or its WebDAV or S3 gateway) and its bytes pass through it. To decide after the pilot.
- **App**: make a change of access immediate (ROADMAP 1). Drop "Later" in the first run and retire the zip and its docs once the team uses the cask.

## 4. Pilot

One shared disk, one or two weeks of real work in CapCut, on the first instance. To measure: scrubbing on uncached clips, uploading footage, first opening of a folder with many videos, how the disk behaves when the line is busy or drops. Every problem noted with what and when: it decides what the app does next.
