01 · Overview

From one disk per Mac to one disk per team

Today every Mac has its own disk, with the metadata in SQLite inside the VM and the S3 keys in a zip. The proposal: one shared disk per team, its metadata in a central Valkey with a live copy inside every Mac's VM, personal access through a login, and a menu bar app that installs and drives everything.

02 · Architecture

Three places, and the file tree on both ends

Each Mac runs the app, the fluix command and a small Linux VM with JuiceFS. The file tree lives in a central Valkey, and the VM keeps a replica of it that the master updates as it changes: JuiceFS reads the tree from that replica, sends its writes to the center, and fetches file contents from S3. The control plane only talks to the app and, as administrator, to Valkey.

VMMIT

macos/vm/ · Lima, Debian 13
  • JuiceFS client and cache
  • Samba on the private link
  • A Valkey replica of the volume's metadata
  • Image and packages shipped, Valkey 8.1.1 from Debian 13 included: no downloads

JuiceFSApache-2.0

patched: spike/juicefs-replica, on v1.4.1
  • Lookups, attributes, listings, xattrs and slice lists from the local replica
  • Writes on the master in one round trip: logic on replica reads, then one script that checks them and applies
  • Read-your-writes from a session counter in the same transaction
  • Mode and lag in .stats: replica, master, offline

Valkey replicaBSD

inside each VM · 127.0.0.1
  • Native replication: the master pushes every change
  • Resumes from a 256 MB backlog, or resyncs in full
  • Over 2 s behind or restarted empty: reads go to the master
  • Authenticates with the Mac's Valkey user

Control planeAGPL-3.0

server/ · FastAPI, React, PostgreSQL · Docker Compose
  • Accounts, magic link sign-in, invites
  • Organizations, volumes, devices, in its own PostgreSQL
  • Creates and deletes the Valkey ACL users
  • Creates volumes (juicefs format), rotates the S3 key
  • Audit log

Valkey, centralBSD

a server in the same region as the bucket
  • One database per volume (JuiceFS keys)
  • An ACL user per Mac, for its writes and its replica
  • appendfsync always, a replica in the datacenter, a daily juicefs dump

Object storageany S3

a bucket per organization
  • Volumes are prefixes inside the bucket
  • One key per organization, stored in the metadata
  • Rotated by pasting a new key, no provider API

Residual risk: the window before rotationA revoked Mac keeps the replica it had, S3 key included, until the app clears it at the next heartbeat; whoever copied the key can delete or download raw blocks until the admin deletes it at the provider. Without metadata the blocks are 4 MB fragments with no names; deletion is the real risk. Mitigations: rotate right after revoking, and bucket versioning as a safety net (an open decision, it bills deleted blocks).
Permissions stay all or nothingEveryone in an organization sees and can delete every file of its volumes. JuiceFS Community has no per-folder permissions; trash (7 days) and the bucket's copy at a second provider cover mistakes. The replicas in the Macs are not a backup: they follow the master, deletions included.

One Valkey user per Mac instead of per person: a lost or stolen laptop is revoked alone, and the person keeps working on the others. Replication copies a whole Valkey instance, not one database: a replica sees every volume on its master, so organizations never share an instance.

What breaks when a piece is missing

DownMounted disksWhat waitsMitigation
Control planekeep workingSign-in, new Macs, revocation, rotationIt holds no file data; restart or redeploy
Central Valkeyread onlyEvery change: saving, renaming, deleting. Browsing and reading go on from each replicaEvery write on disk before the answer, a replica in the datacenter, a daily dump, alert
S3cache onlyUncached reads and every writeWriteback off: a saved file is on S3, never only on a Mac
The Mac's networkread onlySaving fails in 0.1 s; uncached clipsThe whole tree stays browsable; back within 0.2 s of the link returning
The local replicakeep workingNothing; reads cross the network meanwhileBehind over 2 s, stopped or restarted empty: reads go to the master until it catches up
The VMbrief stopUntil the agent restarts itAgent every 2 minutes, health check from inside the VM
The Mac's disk spacecache freedCached clips must download againCeiling and emergency eviction computed on the Mac side
Being refined: slow is not unreachableA master that answers late, for example during a large copy, must not turn the disk read only. Offline will mean unambiguous unreachability, or several failed health checks in a row.

anyone, from the public repo

  • Any S3, a Valkey server, PostgreSQL for the control plane
  • One organization, created at first start
  • Mail through plain SMTP

First instance

a self-hosted install, the first real one
  • Control plane on a Dokploy server
  • Central Valkey and S3 in Milan
  • Replaces the tester's per-Mac disk
  • Volume created fresh: the test volume does not migrate

Hosted service

later, same code
  • Many organizations on one instance
  • Isolation by a Valkey instance and a bucket per organization, not by application filters: replication copies a whole instance
  • The key's scope to its bucket is set by the operator in the provider console

10 · Performance

Measured: shared metadata at local speed

Step 0 ran on 17/10/2026 in a local rig: two JuiceFS clients in containers standing in for two Macs' VMs, each with its local replica, mounted by the Mac over SMB, and the central metadata server behind a simulated 15 ms link, the same footage and the same tests for every option.

Why remote metadata failed first

With PostgreSQL across the link, that listing took 117 s from the Finder and creating one small file about 1.8 s. Inside the VM, without Samba, the same listing took 0.12 s: the database was fine, the number of trips was not.

Making Samba ask less (vetoing ._ files, a local index of Finder attributes) breaks sharing between Macs. What works is making the answers local: a replica of the metadata in every VM, which is what Valkey's native replication gives.

13 · Open decisions

To close before or during the build

Cache on revocation

The cache and the replica hold the organization's footage and file tree on a Mac that is no longer allowed.

the app clears both at the first heartbeat that says revoked.
Metadata cache timeouts

With reads from the local replica, longer JuiceFS cache timeouts save little and delay other people's changes, which now show up in 0.00-0.01 s.

keep the JuiceFS defaults unless the pilot shows otherwise.
Bucket versioning

A safety net for the rotation window, but deleted and compacted blocks stay billed.

on, with a lifecycle rule that expires old versions after a few days.
Where the central Valkey runs

A VPS next to the bucket in Milan, or a managed Valkey in the same region. It needs appendfsync always, a replica and replication open to the Macs.

decided with the first instance, on durability first and price second.
Keeping the JuiceFS patch

The read replica and the one-round-trip writes live in a fork of v1.4.1, to rebuild on every JuiceFS release.

propose it upstream, and pin the version in the package meanwhile.
Homebrew needs administrator rights

Installing Homebrew uses sudo; the app itself does not. It bends a "never compromise" rule.

accepted for now; a DMG into ~/Applications later if a team has standard accounts.
Mockup questions

Text when unreachable, full cache behavior, reconnection interval, "Turn off" or "Eject".

by the concepts on 17/10/2026: Turn off, a full cache frees the least recently used blocks, automatic reconnection every 30 s, settings in their own window. The Unreachable text, drawn before the replica, still has to say the disk is read only rather than closed.
