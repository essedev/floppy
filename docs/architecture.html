01 · Overview

From one disk per Mac to one disk per team

Today every Mac has its own disk, with the metadata in SQLite inside the VM and the S3 keys in a zip. The proposal: one shared disk per team with the metadata in PostgreSQL, personal access through a login, and a menu bar app that installs and drives everything.

02 · Architecture

Three places, three kinds of traffic

Each Mac runs the app, the fluix command and a small Linux VM with JuiceFS. The VM talks to PostgreSQL for the file tree and to S3 for the file contents. The control plane only talks to the app and, as administrator, to PostgreSQL.

server/ · FastAPI, React, PostgreSQL · Docker Compose
  • Accounts, magic link sign-in, invites
  • Organizations, volumes, devices
  • Creates and drops database roles
  • Creates volumes (juicefs format), rotates the S3 key
  • Audit log

PostgreSQLany

managed, same region as the bucket
  • One database per volume (JuiceFS tables)
  • One role per Mac, with access only to its organization's databases
  • Point-in-time recovery plus a daily juicefs dump

Object storageany S3

a bucket per organization
  • Volumes are prefixes inside the bucket
  • One key per organization, stored in the metadata
  • Rotated by pasting a new key, no provider API

Residual risk: the window before rotationA revoked person who copied the S3 key can still delete or download raw blocks until the admin deletes that key at the provider. 09 · Deployments

One codebase, three ways to run it

Self-hosted

anyone, from the public repo
  • docker compose up for the control plane
  • Any S3 and any PostgreSQL
  • One organization, created at first start
  • Mail through plain SMTP

First instance

a self-hosted install, the first real one
  • Control plane on a Dokploy server
  • Managed PostgreSQL and S3 in Milan
  • Replaces the tester's per-Mac disk
  • Volume created fresh: the test volume does not migrate

Hosted service

later, same code
  • Many organizations on one instance
  • Isolation by database grants and a bucket per organization, not by application filters
  • The key's scope to its bucket is set by the operator in the provider console

10 · Performance

Measured today, and the unknown

The unknown that can change the designAll measurements so far had the metadata next to JuiceFS. With PostgreSQL across the internet, browsing a folder of clips and opening a CapCut project pay a round trip per uncached lookup. If the number is bad, the options are longer metadata cache timeouts or moving PostgreSQL closer, and the plan waits for it.

12 · Plan

Order of work

Engineer days with a coding agent, low and high. A guess, except where step 0 replaces it with a measure.

Step 0, the spike

Finder and CapCut on metadata in a remote PostgreSQL: a folder of clips, opening a project, scrubbing. Round trip to the managed database in Milan.
juicefs config with a new key: mounted clients pick it up within a minute, as the JuiceFS docs say.
A client mounts with a role limited to SELECT, INSERT, UPDATE, DELETE on tables it does not own.
Ending the sessions and dropping the role stops a mounted client cleanly, without corrupting the volume.

13 · Open decisions

To close before or during the build

Role per Mac or per person

Per Mac lets a stolen laptop be revoked alone; per person is fewer roles.

per Mac.
Cache on revocation

The cache holds the organization's footage on a Mac that is no longer allowed.

the app clears it at the first heartbeat that says revoked.
Metadata cache timeouts

Longer timeouts mean fewer round trips but slower visibility of other people's changes.

decided on step 0 numbers.
Bucket versioning

A safety net for the rotation window, but deleted and compacted blocks stay billed.

on, with a lifecycle rule that expires old versions after a few days.
Mockup questions

Text when unreachable, full cache behavior, reconnection interval, "Turn off" or "Eject".

with shared PostgreSQL "files will not open until the disk is back" becomes true; the rest at the panel build.
Homebrew needs administrator rights

Installing Homebrew uses sudo; the app itself does not. It bends a "never compromise" rule.

accepted for now; a DMG into ~/Applications later if a team has standard accounts.
