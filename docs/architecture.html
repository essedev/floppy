01 · Overview

From one disk per Mac to one disk per team

Today every Mac has its own disk, with the metadata in SQLite inside the VM and the S3 keys in a zip. The proposal: one shared disk per team, its metadata in a central Valkey with a live copy inside every Mac's VM, personal access through a login, and a menu bar app that installs and drives everything.

02 · Architecture

Three places, and the file tree on both ends

Each Mac runs the app, the floppy command and a small Linux VM with JuiceFS. The file tree lives in a central Valkey, and the VM keeps a replica of it that the master updates as it changes: JuiceFS reads the tree from that replica, sends its writes to the center, and fetches file contents from S3. The control plane only talks to the app and, as administrator, to Valkey.

Residual riskThe window before rotation

A revoked Mac keeps the replica it had, S3 key included, until the app clears it at the next heartbeat; whoever copied the key can delete or download raw blocks until the admin deletes it at the provider. Without metadata the blocks are 1 MB fragments with no names; deletion is the real risk. Mitigations: rotate right after revoking, and bucket versioning as a safety net (an open decision, it bills deleted blocks).

Permissions stay all or nothing

Everyone in an organization sees and can delete every file of its volumes. JuiceFS Community has no per-folder permissions; trash (7 days) and the bucket's copy at a second provider cover mistakes. The replicas in the Macs are not a backup: they follow the master, deletions included.

One Valkey user per Mac instead of per person: a lost or stolen laptop is revoked alone, and the person keeps working on the others. Replication copies a whole Valkey instance, not one database: a replica sees every volume on its master, so organizations never share an instance.

S3Cache onlyUncached reads and every writeWriteback off: a saved file is on S3, never only on a Mac
The Mac's networkRead onlySaving fails in 0.1 s; uncached clipsThe whole tree stays browsable; back 0.9 s after the link returns
The local replicaKeep workingNothing; reads cross the network meanwhileBehind over 2 s, stopped or restarted empty: reads go to the master until it catches up
The VMBrief stopUntil the agent restarts itAgent every 2 minutes, health check from inside the VM

ClosedSlow is not unreachable

A master that answers late, for example during a large copy, must not turn the disk read only. The patch goes offline only on unambiguous unreachability, or after 10 s without any answer from the master. Measured (t13): with the master answering in 1.2 s, give or take 0.6 s, 20 writes went through with no read-only error.

10 · Performance

Measured: metadata at local speed, data close to the line

Two spikes ran on 17/10/2026 in a local rig: two JuiceFS clients in containers standing in for two Macs' VMs, each with its local replica, mounted by the Mac over SMB. The metadata spike put the central server behind a simulated 15 ms link, with the same footage and the same tests for every option; the data-path spike shaped the link to S3 and changed one thing at a time. Both are closed; the data path still has to be confirmed on OVH Milan.

Why remote metadata failed first

With PostgreSQL across the link, that listing took 117 s from the Finder and creating one small file about 1.8 s. Inside the VM, without Samba, the same listing took 0.12 s: the database was fine, the number of trips was not.

Making Samba ask less (vetoing ._ files, a local index of Finder attributes) breaks sharing between Macs. What works is making the answers local: a replica of the metadata in every VM, which is what Valkey's native replication gives.

File data: the data path

The data-path spike (DECISIONS #15): 1 MB blocks instead of 4 MB, a 4 MB readahead instead of JuiceFS's default, and the second patch, which reads whole blocks when the Mac's SMB client sends its 128 KB pieces out of order. At 1 Gbps the short readahead costs some sequential speed (82% of the line against 90%), still 13 times what a 60 Mbps clip needs. Whole-block reads cut the extra download from 12-13% to 4-6%, and the GETs for a clip from 722 to about 550; OVH bills neither requests nor traffic, so four times the requests of 4 MB blocks cost nothing.

The same package on the real service, before the data-path spike: a seek in cache 0-3 ms, like a local disk; a cold seek 0.9 s on average, 1.9 s at worst, because each one downloaded a 4 MB block.

11 · Costs

Cost grows with terabytes, not people

Floppy has no per-person price. Self-hosted, a team pays the storage (about 7.5 EUR/TB on OVH) and a fixed 20-30 EUR for the metadata server, the central Valkey and its replica in the datacenter (an estimate: the host is not chosen yet). Adding a person costs nothing; adding a terabyte costs the storage. The commercial products charge per person.

What the licenses hide

The gap widens with every person, but what is left is the cost of running it: keeping the Valkey up and its backups checked, answering when a Mac does not mount, and carrying the JuiceFS patches across releases (half a day to a day per release that touches them, an estimate). For a small team that time is the real price; it pays off with more people, more terabytes, or data that must stay on infrastructure the team controls.

Build

  • Design on paper. This page's team architecture into ARCHITECTURE.md, and docs/DATABASE_SCHEMA.md for the control plane.
  • Engine. The patched JuiceFS (both patches) and a Valkey replica in the VM's offline package set, floppy status --json, the metadata URL from the app instead of a config file, the SMB password in the Keychain.
  • Fast failure when a file cannot be read. With the network down, a read of blocks not in cache waits for JuiceFS's retries and the Mac's 600 s SMB timeout. It should fail at once, as JuiceMount refuses reads of files not kept offline in 4-67 ms from a local index; it needs to know, per path, what is in the cache.
  • The Mac stays awake while data moves. caffeinate -i during a copy, an upload or a warmup, released a couple of minutes after the traffic stops, so sleep does not cut a transfer halfway. No administrator rights.
  • Control plane. FastAPI and React, accounts with magic link sign-in, organizations, disks, one Valkey user per Mac, key rotation, audit log, Docker Compose for self-hosting.
  • App. Tauri from the Portsage skeleton, built from the concepts: panel, settings, first run.
  • Distribution and first instance. The Homebrew cask, then the first self-hosted instance on Dokploy with a central Valkey and S3 in Milan.

Keeping the JuiceFS patches alive

  • JuiceFS stays pinned at v1.4.1 and moves only when a release brings something needed (a security or bug fix, performance), not with every Floppy release.
  • The patches move from spike/juicefs-replica/ to a branch of a fork (essedev/juicefs), one commit per change, so an update is a rebase.
  • A scheduled GitHub Actions job applies them to each new JuiceFS release and runs the Go tests, so a break shows up before the update is needed.
  • An update ships only after the Go tests, JuiceFS's own Redis metadata tests, the acceptance suite and a run with mixed versions (some Macs on the old JuiceFS, some on the new, one Valkey); if mixed versions do not hold, the control plane enforces a minimum version.
  • Checked on 17/10/2026: no JuiceFS release after v1.4.1 yet; against main, 212 commits later, 25 of the first patch's 27 hunks in redis.go apply, and doCleanStaleSession and doRemoveXattr conflict.
  • Alongside: propose the read replica and the optimistic transactions upstream, so the fork does not have to live forever.

13 · Decisions

Still open, and closed since the proposal

Closed decisions are recorded in docs/DECISIONS.md and cited by number.

Cache on revocation

The cache and the replica hold the organization's footage and file tree on a Mac that is no longer allowed.

ProposalThe app clears both at the first heartbeat that says revoked.
Bucket versioning

A safety net for the rotation window, but deleted and compacted blocks stay billed.

ProposalOn, with a lifecycle rule that expires old versions after a few days.
Where the central Valkey runs

A VPS next to the bucket in Milan, or a managed Valkey in the same region. It needs appendfsync always, a replica and replication open to the Macs.

ProposalDecided with the first instance, on durability first and price second.
Block size and readahead

A cold seek downloads the whole block that holds it, and after a jump the readahead of the position just left keeps the line busy.

Closed1 MB blocks, a fixed 4 MB readahead, whole-block reads in the second patch (DECISIONS #15).
Metadata cache timeouts

With reads from the local replica, longer JuiceFS cache timeouts save little and delay other people's changes, which now show up in 0.00-0.01 s.

ClosedJuiceFS defaults. JuiceFS 1.4's Redis client-side cache stays off: it caches neither listings nor the missing ._ names, and the patch refuses to run with it (DECISIONS #5).
Keeping the JuiceFS patches

The read replica, the one-round-trip writes and the whole-block reads live on top of v1.4.1, to carry across JuiceFS releases.

ClosedPinned, a fork branch with one commit per change and a scheduled job against each release (ROADMAP 3); proposed upstream meanwhile.
Homebrew needs administrator rights

Installing Homebrew uses sudo; the app itself does not. It bends a "never compromise" rule.

ClosedAccepted once, for Homebrew itself (DECISIONS #10); a DMG in ~/Applications stays the fallback if a team has standard accounts.
The name

"Fluix" collided with Fluix Limited in software, and the name ends up in /Volumes/<Name>, which CapCut projects reference.

ClosedFloppy (DECISIONS #14). EUIPO and UIBM are still to check.
Mockup questions

Text when unreachable, full cache behavior, reconnection interval, "Turn off" or "Eject".

ClosedBy the concepts on 17/10/2026 (DECISIONS #12): Turn off, a full cache frees the least recently used blocks, automatic reconnection every 30 s, settings in their own window. The Unreachable text, drawn before the replica, still has to say the disk is read only rather than closed.
